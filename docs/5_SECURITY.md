# Описание мер обеспечения безопасности системы
## Обеспечение безопасности интерфейсов взаимодействия с системой

### Аутентификация и авторизация
- Защищённые методы требуют заголовка `Authorization: Bearer <token>` или `X-API-Key: <token>`.
- Токен хранится в модели `AccessToken`, проверка через класс `AccessTokenAuthentication`.
- При отсутствии или неверном токене возвращается 401 (Problem Details), не 403.
- Разделение ролей:
  - Обычный пользователь видит только свои ресурсы.
  - Администратор (`is_superuser`) – через `IsAdminTokenAuthenticated`.
- Для каждого токена можно задать список заблокированных IP. Запрос с такого IP отклоняется с 403.
- Публичные эндпоинты (регистрация, login, token, waf-status, справочник HTTP) не имеют `authentication_classes`.

### Rate limiting
- Rate limiting: реализован через `ApiRateLimitMiddleware` и Redis. Ограничение — 10 запросов в минуту на IP и на токен. При превышении возвращается 429 с заголовком `Retry-After`.
- Лимит URI: `ApiUriTooLongMiddleware` отклоняет запросы с URI длиннее 2048 символов = 414.
- Лимит тела: ограничение `DATA_UPLOAD_MAX_MEMORY_SIZE`. Превышение = 413.
- Семантика запроса: `ApiSemantic418Middleware` отвечает 418 на неприменимые запросы (например, `coffee`, `BREW`).

- Каждый запрос получает UUIDv7 через `RequestContextMiddleware`.
- UUID пишется в логи (`waf.http`) и возвращается в заголовке `X-Request-Id` и в поле `requestId` ошибок.
- Ошибки  через `custom_exception_handler`  

### Двухфакторная аутентификация (2FA)
- TOTP (`django_otp`) при входе и при выдаче API-токена.
- При включённой 2FA и отсутствии `otp_token` – ответ 409 с требованием кода.


### Веб-интерфейс (HTML)

- CSRF: используется `CsrfViewMiddleware`. Во всех POST-формах обязательно `{% csrf_token %}`. 
- Запрет CSRF в GET: `RejectCsrfTokenInQueryMiddleware` отклоняет запросы с параметром `?csrfmiddlewaretoken=...`  400.
- Сессии: вход через Django sessions; защищённые страницы требуют декоратора `@login_required`.
- Админ-панель: доступ только для суперпользователя (`@user_passes_test(is_superuser)` на маршрутах `/panel/`).
- 2FA: обязательная проверка OTP при входе, если двухфакторная аутентификация подключена.
- OAuth: поддержка GitHub через `django-allauth` (отдельные маршруты `/accounts/`).
- Токен API никогда не передаётся через GET-параметры — только в заголовках.

## Обеспечение безопасности среды эксплуатации ПО
На сервере эксплуатации, где размещен дистрибутив WAF были настроены необходимые механизмы безопасности.
 
### Настройка безопасности удаленного подключения
В конфигурации SSH был запрещен доступ под пользователем `root`. Для настройки работы дистрибутива WAF был создан пользователь `waf_admin` и его рабочая директория. Так как вся архитектура приложения построена на базе Docker-контейнеров, пользователь `waf_admin` был добавлен в группу `docker`.
Конфигурация SSH представлена в листинге ниже.

**Листинг — конфигурация SSH**

```ssh-config
PasswordAuthentication yes
PubkeyAuthentication yes
Port 2223
Match localport 2223
PermitRootLogin no
AllowUsers waf_admin
MaxAuthTries 3
MaxSessions 5
ClientAliveInterval 300
ClientAliveCountMax 2
AllowTcpForwarding no
X11Forwarding no
LogLevel VERBOSE
```
Данная конфигурация позволяет входить пользователям по паролю и SSH-ключам. Порт, который слушает SSH-сервер, настроен на `2223` вместо стандартного, что позволяет снизить количество автоматических атак. Введен запрет на прямые логины через `root`, а также разрешен вход только для пользователя `waf_admin` с ограниченными разрешениями.

Количество попыток ввода пароля до разрыва соединения ограничивается тремя. Максимальное количество соединений ограничено пятью. В качестве дополнительных механизмов безопасности были отключены возможности туннелирования через SSH-туннели и проброс графического интерфейса.

Каждые 300 секунд сервер отправляет клиенту сообщение «keepalive», тем самым проверяя, находится ли клиент на связи. Если клиент не ответил на 2 keepalive-сообщения, сервер закрывает соединение.

В конфигурации `pam.d/common-password` была настроена политика сложных паролей для пользователя. Для подтверждения или смены пароля требуется длина не менее 8 символов, среди которых должна быть хотя бы одна цифра, одна заглавная и одна строчная буквы. Также был введен запрет на содержание в пароле имени пользователя.

В качестве защиты от перебора паролей была использована программа `Fail2ban`. Данная программа в фоновом режиме непрерывно сканирует лог-файл SSH-сервера на наличие неудачных попыток входа. Если за 5 минут происходит 5 неудачных попыток входа от одного пользователя, данному пользователю ограничивается вход на один час. Ограничение накладывается с помощью политик `iptables`. Конфигурация `Fail2ban` для SSH-сервера представлена в листинге ниже.

**Листинг — конфигурация Fail2ban для SSH-сервера**
```fail2ban-config
[sshd]
enabled = true
port = 2223
filter = sshd
logpath = /var/log/auth.log
maxretry = 3
bantime = 3600
findtime = 300
action = iptables-multiport[name=ssh, port="2223", protocol=tcp]
```

### Настройка межсетевого экрана

Для правильной работы WAF необходим доступ из внешней сети для следующих портов:

| Порт | Назначение |
|------|------------|
| 80 | HTTP Redirect — перенаправляет на порт 1443 с HTTPS-подключением |
| 1443 | Взаимодействие с защищаемым приложением через WAF |
| 8001 | Взаимодействие с админ-панелью и дашбордом |
| 3001 | Просмотр метрик Grafana |

Также для правильной работы Docker были добавлены правила для работы с сетью `172.16.0.0/12`.

### Доступ к приложению через веб-сервер (Nginx) и защитой проколом TLS

Был настроен веб-сервер `Nginx` с защитой протоколом `TLS`. Nginx выступает в роли шлюза и работает в режиме обратного прокси, направляя весь трафик к запущенному веб-приложению.
Для работы по HTTPS был настроен TLS-сертификат с помощью утилиты `Certbot`. Срок службы сертификата составляет один год. Сертификат настроен на домен `403118.vm.spacecore.network`.
С помощью строки `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;` в конфигурации Nginx был добавлен заголовок `HSTS`. В параметрах заголовка был указан срок действия политики в один год и требование применять `HSTS` также ко всем поддоменам.
